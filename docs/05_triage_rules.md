# Triage Rules (Severity / Priority)

## 1. 목적
본 문서는 이슈(버그/개선/문의)를 QA 관점에서 일관되게 분류하고,
사용자 영향과 비즈니스 리스크를 기준으로 우선순위를 결정하기 위한 기준을 제공합니다.

---

## 2. 용어 정의
- Severity(심각도): "사용자/서비스에 미치는 영향" 기준
- Priority(우선순위): "언제/어떻게 대응할지" 결정 기준(릴리즈 일정/비즈니스 영향 포함)

---

## 3. Severity 기준 (S1~S4)

### S1 (Critical)
- 서비스 사용이 불가능하거나, 핵심 기능이 전면 중단되는 수준
- 결제/주문/가입 등 핵심 트랜잭션이 완료되지 않음
- 데이터 유실/손상 가능성, 보안 사고 가능성
- 앱/웹 크래시, 무한 로딩, 서버 5xx 다발 등

### S2 (High)
- 핵심 기능은 일부 동작하지만, 사용자 진행이 자주 막히거나 우회가 어려움
- 잘못된 결과(금액/수량/상태)가 표시되는 등 신뢰도에 영향
- 특정 환경(브라우저/디바이스)에서 재현률이 높음

### S3 (Medium)
- 기능은 동작하나 UX 저하, 메시지/가이드 부족, 경미한 오동작
- 우회 방법이 존재하며 사용자 영향이 제한적

### S4 (Low)
- 오탈자/정렬/경미한 UI 깨짐 등 기능 영향이 거의 없음
- 개선 사항(Enhancement)에 가까움

---

## 4. Priority 기준 (P0~P3)

### P0 (즉시 대응)
- S1 수준이거나, 서비스 장애/핵심 트랜잭션 차단
- 배포 차단(Blocking) 이슈
- 핫픽스/롤백 고려 대상

### P1 (이번 릴리즈 내 해결 권장)
- S2 수준의 이슈
- 사용자 불만/리뷰/CS 유입 가능성이 높음
- 핵심 플로우에 영향을 주는 결함

### P2 (다음 릴리즈/스프린트에서 처리)
- S3 수준, 우회 가능, 영향 범위 제한
- 일정/리소스 고려하여 계획 반영

### P3 (백로그)
- S4 수준, 개선/정리 성격
- 우선순위 낮음

---

## 5. 트리아지 진행 절차 (Workflow)
1. 이슈 접수(재현 가능 여부/환경/로그 확인)
2. 재현 및 영향 범위 확인(몇 % 재현, 어떤 사용자/환경 영향)
3. Severity 판단(사용자 영향 중심)
4. Priority 판단(릴리즈/비즈니스/운영 리스크 반영)
5. 담당자 지정 및 일정 합의
6. 수정 후 재검증(Regression 포함)
7. 릴리즈 노트/완료 기준 업데이트

---

## 6. 실무 적용 예시
- 결제 완료가 되지 않음 → Severity S1 / Priority P0
- 장바구니 수량 배지가 간헐적으로 반영되지 않음(재현률 높음) → S2 / P1
- 필수값 누락 시 안내 메시지가 불명확함(BR-001) → S3 / P2 (서비스 정책에 따라 P1 가능)
- 오탈자 1건 → S4 / P3

---

## 7. 참고
- Severity와 Priority는 항상 1:1로 고정되지 않으며,
  릴리즈 일정/사용자 영향/대응 비용을 함께 고려하여 결정합니다.
